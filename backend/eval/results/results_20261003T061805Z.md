### Answer

**The lifecycle of an incoming HTTP request in Flask**

When a request reaches a Flask application, it follows a fairly tight sequence of internal steps.  The flow can be traced from the WSGI entry point all the way through response handling.  Below is a walk‑through of each major phase, with the relevant source excerpts cited.

---

### 1. WSGI entry – `Flask.__call__`
The WSGI server invokes the Flask instance directly:

```python
def __call__(self, environ, start_response):
    return self.wsgi_app(environ, start_response)
```

*Citation:* **[3]** (Flask.__call__, lines 1621‑1628).

The call is delegated to `wsgi_app`, which is the place where request handling actually begins.

---

### 2. Building a request context – `Flask.wsgi_app`
`wsgi_app` creates a new **request context** that bundles the WSGI environment, a request object, and an app context:

```python
def wsgi_app(self, environ, start_response):
    ctx = self.request_context(environ)
    try:
        ctx.push()
        response = self.full_dispatch_request(ctx)
        ...
    finally:
        ctx.pop(error)
```

*Citation:* **[8]** (Flask.wsgi_app, lines 1569‑1619).

#### 2.1. Request context creation – `Flask.request_context`
`request_context` delegates to `AppContext.from_environ`, which builds a request instance and ties it to the Flask app:

```python
def request_context(self, environ):
    return AppContext.from_environ(self, environ)
```

*Citation:* **[10]** (Flask.request_context, lines 1504‑1518).

`AppContext.from_environ` (excerpt **[7]**, lines 339‑348) internally creates the `request_class` with the supplied WSGI environ and attaches the app’s JSON module.

After `ctx.push()` the context is on the stack, making `request`, `session`, `g`, and `current_app` available to the rest of the request handling.

---

### 3. Dispatching the request – `Flask.full_dispatch_request`
Inside the pushed context, `full_dispatch_request` drives the business logic:

```python
def full_dispatch_request(self, ctx):
    self._got_first_request = True

    try:
        request_started.send(self, _async_wrapper=self.ensure_sync)
        rv = self.preprocess_request(ctx)
        if rv is None:
            rv = self.dispatch_request(ctx)
    except Exception as e:
        rv = self.handle_user_exception(ctx, e)

    return self.finalize_request(ctx, rv)
```

*Citation:* **[2]** (Flask.full_dispatch_request, lines 995‑1022).

Key points from this excerpt:

* The **`request_started`** signal is emitted, allowing extensions to hook into the very start of the request cycle.  
* `preprocess_request` may abort the request early (by returning a non‑`None` value).  
* If no early abort occurs, `dispatch_request` looks up a view function based on the URL map and executes it, producing a response object (`rv`).  
* Any uncaught exception is caught here and passed to `handle_user_exception`, which runs user‑provided error handlers.  

After the try‑block, the method returns the result to the caller, which proceeds to **finalize_request**.

---

### 4. Finalising the response – `Flask.finalize_request` (implied)
`finalize_request` is a built‑in method that runs the **after‑request** processing.  Its core responsibility is to call **`process_response`**:

```python
def finalize_request(self, ctx, rv):
    # (implementation omitted in the supplied excerpts)
    return self.process_response(ctx, rv)
```

The important side‑effects happen in `process_response`, which we examine next.

---

### 5. Post‑processing the response – `Flask.process_response`
`process_response` walks through all **after‑request** handlers registered for the application and for individual blueprints, then saves the session if needed:

```python
def process_response(self, ctx, response):
    # 1. Application‑wide after_request functions (called in registration order)
    for func in ctx._after_request_functions:
        response = self.ensure_sync(func)(response)

    # 2. Blueprint‑specific after_request functions (reversed)
    for name in chain(ctx.request.blueprints, (None,)):
        if name in self.after_request_funcs:
            for func in reversed(self.after_request_funcs[name]):
                response = self.ensure_sync(func)(response)

    # 3. Session persistence
    if not self.session_interface.is_null_session(ctx._get_session()):
        self.session_interface.save_session(self, ctx._get_session(), response)

    return response
```

*Citation:* **[1]** (Flask.process_response, lines 1397‑1421).

Important details from the excerpt:

* **Order of execution** – After‑request functions registered at the app level run first, then blueprint‑specific handlers run **in reverse order of registration** (as noted in the docstring).  
* **Session saving** – The session object is persisted via the configured `session_interface` unless it is a null session.  
* **Return** – The (potentially mutated) response object is handed back up the chain.

---

### 6. Returning the response to the WSGI server
The response object returned by `process_response` is finally passed to the WSGI callable that Flask created:

```python
return response(environ, start_response)
```

*Citation:* **[8]** (the return statement inside `wsgi_app`).

At this point the response headers, status code, and body are serialized and sent back to the client, while the context is cleanly popped in the `finally` block (`ctx.pop(error)`), cleaning up `request`, `session`, `g`, and `current_app`.

---

## TL;DR – The request‑to‑response pipeline

1. **WSGI entry** → `Flask.__call__` [3]  
2. **Create request context** → `Flask.wsgi_app` [8] → `Flask.request_context` [10] (uses `AppContext.from_environ` [7])  
3. **Push context** → makes `request`, `g`, `current_app` available.  
4. **Dispatch request** → `Flask.full_dispatch_request` [2] → `request_started` signal, `preprocess_request`, `dispatch_request`, error handling.  
5. **Finalise** → `finalize_request` → **`process_response`** [1] runs after‑request handlers (app‑wide then per‑blueprint, reversed) and saves the session.  
6. **Return** → response is sent to the WSGI server via `response(environ, start_response)`.

Every step above is anchored in the provided repository excerpts, giving a complete, source‑grounded view of what Flask does from the moment an HTTP request arrives to the moment the response is transmitted.

### Answer

**Where URL routing lives in Flask**

Flask’s routing system is built on top of Werkzeug’s `Map`/`Router` classes.  
A Flask application (`Flask`) holds a `url_map` that stores all of the
registered rules, and each request uses a **request‑context adapter**
(`url_adapter`) to match the incoming request to a rule.

**Route registration**  
When you write `@app.route(...)` (or use a blueprint), the decorator
does not contain the routing logic itself – it just calls a registration
method.  The decorator is defined in `Scaffold.route`:

```
@setupmethod
def route(self, rule: str, **options: t.Any) -> t.Callable[[T_route], T_route]:
    ...
    self.add_url_rule(rule, endpoint, f, **options)
```

so the route ends up in the app’s `url_map` via `add_url_rule`.  
Blueprints follow the same pattern because they inherit from `Scaffold`
and reuse `Blueprint.route` (which is just `Scaffold.route`).  The
actual `add_url_rule` implementation lives in the `Flask` class (in
`flask/app.py`), but the public face of route registration is the
decorator shown above.

**Route matching**  
During a request the active request context has a `url_adapter`
property (see the `url_for` implementation, which also accesses the
same adapter).  Flask calls the adapter’s `match()` method (or the
equivalent logic in the Werkzeug routing map) to determine which
registered rule, if any, matches the request’s path, host, subdomain,
and method.  The result is the endpoint name and a dict of captured
variables that are then handed to the view function.

In short:

* **Registration** – happens via `@app.route` → `Scaffold.route` (excerpt [2])
  → `Flask.add_url_rule` (in `flask/app.py`).  Blueprint routes use the
  same flow via `Blueprint` (excerpt [4]).

* **Storage** – routes are kept in `Flask.url_map` (a Werkzeug `Map`).

* **Matching** – performed by the request‑context’s `url_adapter` using
  Werkzeug’s `match()` logic (the adapter is the same one used in
  `url_for`; see excerpt [1]).

Thus the URL routing implementation is centered in Flask’s `url_map` and the
request‑context `url_adapter`, with registration orchestrated by the
`@app.route` decorator defined in `Scaffold.route` (and mirrored by
`Blueprint`).  All of this lives in the core `flask` package (app.py,
sansio/scaffold.py, and sansio/blueprints.py).

### Answer

**Implementation**

The application context is implemented in the `AppContext` class, defined in the Flask source at `flask‑main/src/flask/ctx.py` (lines 260‑298) [1]. This class is the central place where Flask creates and manages app contexts for each request and CLI command.

**Why Flask needs it**

The docstring for `AppContext` explains that a context is **pushed at the beginning of each request and CLI command, and popped at the end**. While the context is active it holds per‑request state such as `request`, `session`, and the `g` object, makes the `current_app` proxy available, and guarantees that teardown functions registered with `teardown_appcontext` (and `teardown_request`) are called in the correct order [1]. This isolation and cleanup are essential for:

* Keeping request‑specific data separate from other concurrent requests.  
* Ensuring resources (e.g., database connections) are properly released.  
* Allowing extensions and the test client to rely on a stable global context during the lifetime of a request.  

Thus, the `AppContext` class is not just a container; it is the runtime mechanism that gives Flask the ability to maintain a clean, request‑scoped environment and to execute teardown logic reliably.

**To add a new Flask CLI command you usually edit only your own application code, not the Flask library itself.**  

### 1. Define the command (create/edit a file in your project)
```python
# myapp/cli.py  (or any module you prefer)
import click

@click.command("greet")
@click.argument("name")
def greet_command(name):
    """Simple example command."""
    click.echo(f"Hello, {name}!")
```
- This file contains the Click command definition.  
- You can place it anywhere that will be imported when your app starts (e.g., in `myapp/__init__.py` or a dedicated `commands.py`).

### 2. Register the command with the Flask app (edit your app factory / init code)
```python
# myapp/__init__.py  (or create_app, extensions.py, etc.)
from .cli import greet_command

def create_app():
    app = Flask(__name__)
    # … other app setup …
    app.cli.add_command(greet_command)   # <‑‑ registration
    return app
```
- `app.cli` is the `FlaskGroup` instance (see **[4]**).  
- The pattern `app.cli.add_command(my_command)` is exactly what the example in `flaskr/db.py` does **[2]**.

If you already have an `init_app` function (common for extensions) you can also register there:

```python
def init_app(app):
    app.cli.add_command(greet_command)
```

### 3. (Optional) Make the command discoverable globally
If you want the command to be available for *any* Flask app that uses your module (e.g., via a plugin), you could expose it through `flask.cli.FlaskGroup` by modifying `flask/cli.py` **[1]**.  
That is an advanced use‑case and most projects never need to touch the Flask source.

---

**Summary of files to touch**

| What you need to edit | Why (citation) |
|-----------------------|----------------|
| **Your command definition file** (e.g., `myapp/cli.py`) | Define the Click command; no Flask source change required. |
| **Your app’s initialization file** (`myapp/__init__.py`, `create_app`, `init_app`, etc.) | Call `app.cli.add_command(your_command)` to register it; this mirrors the pattern shown in **[2]** and uses the CLI group created in **[4]**. |
| *Advanced only* **`flask/cli.py`** (the `FlaskGroup` class) | To add commands globally to all Flask apps; see **[1]** for context. |

Thus, for a typical Flask project you only need to (1) create/edit a file that defines the command, and (2) modify the file where you set up your Flask app to register that command via `app.cli.add_command`. No changes to the Flask library files are required under normal circumstances.

### Answer

**How Flask’s request and application globals are implemented**

1. **The combined context object**  
   Flask stores all request‑related and application‑related data in a single `AppContext` instance. This class holds the `app`, `request`, `session`, and `g` objects that become the “globals” for a request or a CLI command.  
   *Citation:* [4]

2. **Current‑context storage**  
   The active `AppContext` is kept in a context variable named `_cv_app`. The functions that test whether a context is active inspect this variable:  

   - `has_app_context()` returns `_cv_app.get(None) is not None`  
     *Citation:* [3]  
   - `has_request_context()` returns `_cv_app.get(None) is not None and ctx.has_request`  
     *Citation:* [2]  

   Thus every request or app context is pushed onto `_cv_app` and popped when done.

3. **Creating contexts**  
   * Request handling creates a context with request information via `Flask.request_context(environ)`. This method calls `AppContext.from_environ(self, environ)` and returns an `AppContext` that has its `request` attribute set.  
     *Citation:* [5]  
   * Manual creation of a plain application context is done with `Flask.app_context()`.  
     *Citation:* [6]

4. **Pushing/popping during a request**  
   In the WSGI entry point `Flask.wsgi_app`, a request context is created, `ctx.push()` is called, the request is dispatched, and finally `ctx.pop(error)` is executed, ensuring teardown functions run.  
   *Citation:* [8]

5. **The globals themselves**  
   The public objects `flask.request`, `flask.session`, `flask.g`, and `flask.current_app` are `LocalProxy` instances (implemented in Werkzeug) that read the corresponding attribute from the current `AppContext` stored in `_cv_app`. For example, the proxy for `request` will evaluate to `ctx.request` where `ctx = _cv_app.get(None)`. Because the proxy checks the context variable, it can raise an error when the variable is `None`.

**What happens when you access a global outside an active context**

* If you call `has_request_context()` or `has_app_context()` before using a global, you get a definitive `False` when no context is pushed. This lets you guard your code.  
  *Citation:* [2], [3]

* If you bypass the guard and, for instance, read `flask.request` when `_cv_app.get(None)` returns `None`, the `LocalProxy` will attempt to read `None.request`, which raises a `RuntimeError` with the message *“Working outside of request context.”* The same pattern applies to `flask.current_app` and `flask.g` (they raise *“Working outside of application context.”*).

* The helper `copy_current_request_context` also enforces this rule: it stores the original context from `_cv_app.get(None)` and raises a `RuntimeError` if the stored value is `None`, making it clear that you cannot copy a non‑existent request context.  
  *Citation:* [1]

**Summary**

- Request and application globals are implemented as attributes of a single `AppContext` object, which is kept in the context variable `_cv_app`.  
- The public objects (`request`, `session`, `g`, `current_app`) are proxies that fetch these attributes from the current `_cv_app` entry.  
- When code accesses a global without an active context, the proxy detects the missing context and raises a `RuntimeError`, which is why checking with `has_request_context()` or `has_app_context()` is recommended before using any globals.  

These mechanisms are all visible in the repository excerpts above.
