### Answer

**Architecture Overview**

The Flask project is organized around a small set of core classes that together provide a complete WSGI web framework. The public API presented to developers is the **`Flask`** class, which builds on the lower‑level **`App`** class (defined in `flask.sansio`). Two of the most common extensions—**template rendering** and **session handling**—are implemented as separate, swappable components: a custom **`Environment`** for Jinja and a **`SessionInterface`** for persisted sessions.

Below is a concise description of each component, how they are related, and the flow of responsibilities.

---

### Core Components

| Component | Location (excerpt) | Primary Responsibility |
|-----------|-------------------|--------------------------|
| **`Flask`** (public API) | [2] (flask/app.py:110‑205) | The class users import to create an application instance. It serves as the central registry for view functions, URL rules, template configuration, static files, and configuration values. |
| **`App`** (sans‑IO core) | [3] (flask/sansio/app.py:59‑154) | The foundational WSGI application class that `Flask` inherits from. It contains the bulk of the request handling, routing, and resource‑loading logic that is independent of Flask‑specific conveniences. |
| **`Environment`** (Jinja) | [1] (flask/templating.py:36‑40) | A Jinja environment subclass that knows about Flask’s blueprint system, allowing template names to be automatically prefixed with a blueprint’s name when needed. |
| **`SessionInterface`** (sessions) | [4] (flask/sessions.py:100‑135) | The abstract base class defining how sessions are opened, saved, and null‑handled. Applications replace the default secure‑cookie interface by assigning a custom implementation to `app.session_interface`. |

---

### How the Pieces Fit Together

1. **Application Creation**  
   When a developer writes `app = Flask(__name__)` they instantiate the `Flask` class (public façade) [2]. Because `Flask` extends `App`, the new object automatically gains the core functionality defined in `App` (routing, configuration loading, static‑file serving, etc.) [3].

2. **Template Rendering**  
   All template rendering goes through the custom Jinja **`Environment`** [1]. By subclassing Jinja’s default environment, `Environment` can detect the current blueprint (if any) and prepend its name to template references, ensuring that a template used from within a blueprint is resolved correctly. Flask’s internal template helper methods (e.g., `render_template`) rely on this environment.

3. **Session Management**  
   The `Flask` instance provides a `session_interface` attribute (documented in the `SessionInterface` excerpt) [4]. By default this attribute holds an instance of the secure‑cookie based session interface. During a request Flask calls `open_session` on the interface to obtain a session object and later calls `save_session` to persist any changes. Developers can swap the entire implementation by assigning a custom `SessionInterface` subclass to `app.session_interface`, allowing storage in databases, Redis, etc.

4. **Request Flow (high‑level)**  
   - A WSGI request reaches `Flask`/`App`.  
   - The request context is created (handled by `App` code not shown here).  
   - Blueprint‑aware **`Environment`** is used whenever a template is rendered.  
   - The **`SessionInterface`** is queried for a session, which is attached to the request context.  
   - View functions are dispatched, and the response is returned.

   Because the core request handling lives in `App` while the public entry point is `Flask`, changes to the internal request processing do not affect the stable API presented to users.

---

### Extensibility Points

- **Custom Environments** – Subclass `Environment` and replace `app.jinja_env` (or similar) to add filters, globals, or custom loaders.
- **Custom Sessions** – Provide a new `SessionInterface` subclass and assign it to `app.session_interface` [4]; the framework will automatically use it for all requests.
- **Blueprint Integration** – The `Environment` already knows about blueprints; extending it can add more sophisticated name‑prefixing or namespace handling.

---

### Summary

- **`Flask`** ([2]) is the developer‑facing façade.  
- It **inherits** from **`App`** ([3]), which supplies the underlying WSGI machinery.  
- **`Environment`** ([1]) provides blueprint‑aware template rendering.  
- **`SessionInterface`** ([4]) abstracts session storage and can be swapped at will.

These components cooperate through a well‑defined hierarchy: `Flask` → `App` (core) + `Environment` (templates) + `SessionInterface` (sessions). This separation keeps the framework small, testable, and extensible while presenting a simple, consistent API to application developers.

### Answer

**Flask does not provide a built‑in database‑connection manager.**  
All the “open‑a‑connection at the start of a request and close it at the end” pattern is left to the developer (or to extensions such as Flask‑SQLAlchemy). What Flask does give you is the request‑lifecycle machinery that makes it easy to implement that pattern.

### How the lifecycle works

1. **Request handling pushes an `AppContext`.**  
   For every request (and CLI command) Flask pushes an :class:`.AppContext` onto the context stack. While the context is active the special objects ``current_app`` and ``g`` are available [#1]. ``g`` is the standard place to stash a DB connection for the duration of the request.

2. **You open the connection early.**  
   The simplest place is a ``before_request`` handler, inside a view, or even inside the ``app_context`` returned by ``app.app_context()``:

   ```python
   @app.before_request
   def before_request():
       g.db = sqlite3.connect('mydb.sqlite')
   ```

3. **You close the connection when the request ends.**  
   Flask lets you register teardown callbacks with ``teardown_request`` (for request‑scoped cleanup) or ``teardown_appcontext`` (for app‑scoped cleanup). Those callbacks are executed when the ``AppContext`` is popped:

   ```python
   @app.teardown_request
   def teardown_request(exception=None):
       db = getattr(g, 'db', None)
       if db is not None:
           db.close()
   ```

   The same idea can be expressed with the ``after_this_request`` decorator, which adds a function to the request‑specific teardown list:

   ```python
   @app.route('/')
   def index():
       @after_this_request
       def close_db(response):
           db = getattr(g, 'db', None)
           if db is not None:
               db.close()
           return response
       g.db = sqlite3.connect('mydb.sqlite')
       return 'Hello'
   ```

   The ``after_this_request`` implementation lives in ``flask/ctx.py`` and appends the function to ``ctx._after_request_functions`` [#2].

4. **Where the teardown runs.**  
   The description of ``AppContext`` explicitly states that *“When the context is popped, it will evaluate all the teardown functions registered with :meth:`~flask.Flask.teardown_request` (if handling a request) then :meth:`.Flask.teardown_appcontext`.”* This is the implementation that actually runs the callbacks you registered in steps 3 and 4 [#1].

### Where the behavior is implemented in the source

| Feature | Source file & location (excerpt) | What it does |
|---------|----------------------------------|--------------|
| **AppContext creation & teardown** | `flask/ctx.py:260‑298` (excerpt #1) | Defines the ``AppContext`` class, pushes/pops contexts and runs ``teardown_request`` / ``teardown_appcontext`` when the context ends. |
| **``g`` and ``current_app`` become available** | `flask/ctx.py:260‑298` (excerpt #1) | Documents that ``g`` is available while an ``AppContext`` is active. |
| **Adding request‑scoped cleanup** | `flask/ctx.py:118‑148` (excerpt #2) | ``after_this_request`` decorator registers a function in the current request’s teardown list. |
| **Creating an app context manually** | `flask/app.py:1484‑1502` (excerpt #7) | ``Flask.app_context()`` returns a new ``AppContext`` you can ``with``‑block for set‑up/teardown. |

Because the repository snippets do not contain any dedicated DB‑connection code, the **database‑connection handling is entirely custom** and relies on the **context‑lifecycle hooks** described above. Extensions like **Flask‑SQLAlchemy** follow exactly this pattern: they store a connection (or engine/session) on ``g`` in a ``before_request``‑style callback and close it in a ``teardown_request`` callback.

#### Bottom line

- **Flask itself:** No automatic DB‑connection opening/closing. It only provides the **request/app context** infrastructure (implemented in `flask/ctx.py` and exposed via `Flask.app_context()`, `teardown_request`, `after_this_request`, etc.) that you can use to manage DB connections yourself.
- **Typical pattern:** Open the connection early (e.g., in a ``before_request`` or a view), store it on ``g``, and close it in a teardown function (``teardown_request`` or ``after_this_request``). The teardown execution is performed by the ``AppContext`` when its context is popped, as documented in excerpt #1.

**Flask’s request‑to‑response pipeline (as shown in the source excerpts)**  

| Step | What happens | Source citation |
|------|--------------|-----------------|
| **1. WSGI entry** | The WSGI server calls the Flask instance. The instance’s `__call__` method (excerpt [3]) forwards the call to `self.wsgi_app`. | [3] |
| **2. Build a request context** | `wsgi_app` (excerpt [8]) creates an :class:`.AppContext` by invoking `self.request_context(environ)`. `request_context` (excerpt [10]) delegates to `AppContext.from_environ` (excerpt [7]), which constructs a :class:`.Request` object from the WSGI environ and returns a new app context that holds that request. | [8], [10], [7] |
| **3. Activate the context** | The newly created context is pushed with `ctx.push()` (excerpt [8]), making `.request`, `.current_app`, `.g`, and `.session` available for the duration of the request. | [8] |
| **4. Dispatch the request** | While the context is active, `wsgi_app` calls `self.full_dispatch_request(ctx)` (excerpt [8]). `full_dispatch_request` (excerpt [2]) sends the `request_started` signal, runs `preprocess_request`, then `dispatch_request` to locate the view function. If an exception propagates, it is caught and `handle_user_exception` is invoked; otherwise the result (`rv`) is passed to `finalize_request`. | [8], [2] |
| **5. Finalise the response** | `full_dispatch_request` returns `self.finalize_request(ctx, rv)`. `finalize_request` (not shown in the excerpts) calls `process_response` (excerpt [1]) to apply any *after‑request* hooks. `process_response` iterates over `ctx._after_request_functions` and, for each blueprint, over `self.after_request_funcs[name]` in reverse registration order, invoking each function (with `ensure_sync`). Finally, if the session is not a null session, `session_interface.save_session` is called. | [2], [1] |
| **6. Return a WSGI iterable** | The response object returned by `process_response` is the value that `wsgi_app` hands back to the WSGI server via `return response(environ, start_response)` (excerpt [8]). The server then writes the response body to the client. | [8] |

**Key points from the excerpts**

* **Entry point** – The WSGI server only ever calls `Flask.__call__` (`[3]`), which simply delegates to the pluggable `wsgi_app`. This design lets middleware replace `app.wsgi_app` without losing access to the original Flask methods.  
* **Context creation** – `request_context` (`[10]`) uses the class‑method `AppContext.from_environ` (`[7]`) to attach a fresh :class:`.Request` instance to the app context. This is the sole place where the WSGI environ is turned into a Flask request object.  
* **Request handling** – `full_dispatch_request` (`[2]`) encapsulates the whole “dispatch‑and‑catch‑errors” logic. The `try…except` block shows that any uncaught exception is redirected to `handle_user_exception` (or re‑raised), guaranteeing that a response is always produced (or an error is propagated).  
* **Response processing** – `process_response` (`[1]`) is where Flask applies all *after‑request* callables (both app‑wide and blueprint‑scoped) and persists the session. The order of execution follows Flask’s documented behavior: app‑wide after‑request functions run first (in registration order), then blueprint after‑request functions in reverse registration order, and finally the session is saved if present.  
* **Session handling** – The check `if not self.session_interface.is_null_session(ctx._get_session()):` (excerpt [1]) ensures that only non‑empty sessions trigger a save, avoiding unnecessary writes for requests that never modified the session.

Together, these excerpts describe the complete flow: a WSGI request reaches `Flask.__call__`, builds a request‑bound app context, processes the request (including error handling), runs after‑request hooks via `process_response`, saves the session, and finally returns a WSGI‑compatible response iterable to the server.

| **Route registration** | The `route` decorator in `flask/sansio/scaffold.py` (excerpt 2). The decorator creates a wrapper that calls `self.add_url_rule`, which registers the view function with a URL rule. | `@setupmethod def route(self, rule: str, **options: t.Any) -> t.Callable[[T_route], T_route]: … def decorator(f): self.add_url_rule(rule, endpoint, f, **options); return f` |
| **Common base for registration** | `flask/sansio/scaffold.py` defines the `Scaffold` class (excerpt 7). Both `Flask` and `Blueprint` inherit from `Scaffold`, so they share the same registration machinery (`add_url_rule`). | `class Scaffold: …` |
| **Storage of registered routes** | The application’s `url_map` holds all rules. The CLI command `routes` (excerpt 3) accesses them via `current_app.url_map.iter_rules()`. | `rules = list(current_app.url_map.iter_rules())` |
| **Matching incoming requests & building URLs** | The actual path‑matching and URL‑building are delegated to the **Werkzeug routing adapter** (`url_adapter`). In the request context Flask has `ctx.url_adapter` (excerpt 1) and `url_for` uses `url_adapter.build(...)` to convert an endpoint and values into a concrete URL. The same adapter is used by the request dispatcher to match a request path to a rule, though the dispatch logic itself is not shown in the excerpts. | `rv = url_adapter.build(endpoint, values, method=_method, url_scheme=_scheme, force_external=_external)` |

**How routes are matched to view functions**

1. **Registration** – When you decorate a function with `@app.route('/')`, the `Scaffold.route` method (excerpt 2) is invoked. It calls `add_url_rule`, which adds a `werkzeug.routing.Rule` to the app’s `url_map`. This stores the mapping from a URL pattern (e.g., `'/'`) to an endpoint name and the view function (excerpt 7 confirms this is the shared behavior for both `Flask` and `Blueprint`).

2. **Lookup during a request** – When a request arrives, Flask creates a `url_adapter` for the current request context (`ctx.url_adapter` in excerpt 1). The adapter uses the app’s `url_map` to **match** the request path against the registered `Rule` objects, selecting the appropriate endpoint. The matched endpoint is then used to retrieve the associated view function (this matching is performed by Werkzeug’s routing engine, accessed via the adapter).

3. **URL generation** – The `url_for` method (excerpt 1) also uses the same `url_adapter`. It calls `url_adapter.build` with the endpoint and any supplied values to **construct** the concrete URL string, applying defaults, anchors, schemes, etc. The `url_adapter` is therefore the single component that both *matches* incoming requests and *builds* outbound URLs.

**Summary**

- The **registration** of routes is implemented in the `Scaffold` class (excerpt 7) via the `route` decorator (excerpt 2) and its underlying `add_url_rule` method.
- All registered routes are stored in the app’s `url_map` (excerpt 3).
- The **matching** of incoming requests and the **building** of URLs are delegated to Werkzeug’s routing adapter (`url_adapter`), which is exposed through the request context (`ctx.url_adapter`) and used by `url_for` (excerpt 1).

These pieces together constitute Flask’s URL‑routing implementation.

**Question:** Where is the application context implemented, and why does Flask need it? Ground the answer in the repository and cite sources using numbered citations like [1] and [2].

### Answer

**Implementation location**

The application context is realized by the `AppContext` class, which is defined in the file `flask/ctx.py` [1].

**Why Flask needs it**

- **Per‑request isolation** – `AppContext` is pushed at the start of each request and CLI command and popped at the end. While active it holds references to the `app`, the current `request`, and (on first access) the `session`, providing handlers with a stable environment [1].

- **Teardown handling** – When the context is popped, Flask runs any functions registered with `teardown_request` (for requests) and `teardown_appcontext`, ensuring resources are cleaned up in the correct order [1].

- **Debugger and test client support** – The interactive debugger and the test client can preserve the context after a request ends so that `request` remains accessible. If teardown functions have already closed resources (e.g., database connections), the context will be popped again later, running those teardown functions a second time [1].

- **Access point for developers** – Developers are directed to use the `Flask.app_context` method (referenced in the `AppContext` docstring) to create an app context when needed during setup [1].

Together, these behaviors let Flask maintain separate state for each request or CLI command, guarantee proper cleanup, and support debugging and testing scenarios.

### Answer

To add a new Flask CLI command you don’t have to edit the core Flask code – you just need to register the command with the **Flask app’s CLI group**. In the Flask repository the relevant pieces are:

1. **`flask/cli.py` – the `FlaskGroup` class**  
   This is the CLI group that supports loading additional commands from the configured Flask app. It gives you the hooks for custom scripts and for adding the default `run` and `shell` commands. [1]

2. **`flask/app.py` – `Flask.__init__`**  
   Every `Flask` instance creates its own CLI group:  

   ```python
   self.cli = cli.AppGroup()
   ```  
   [4]  

   This `self.cli` attribute is what you use to attach new commands.

3. **Example pattern – `examples/tutorial/flaskr/db.py`**  
   The tutorial shows the idiomatic way to expose a command:  

   ```python
   def init_app(app):
       """Register database functions with the Flask app."""
       app.teardown_appcontext(close_db)
       app.cli.add_command(init_db_command)   # <‑‑ register the command
   ```  
   [2]

Putting it together, the typical workflow is:

| What you edit | Where (in your own project) | How you do it |
|---------------|----------------------------|--------------|
| **Define the command** | In a module such as `myapp/cli.py` or directly in `myapp/__init__.py` | Create a function decorated with `@app.cli.command()` or build a `click.Command` object. |
| **Register the command** | In the same module (or in an `init_app`/`create_app` hook) | Call `app.cli.add_command(your_command)` (or use the decorator which does this automatically). |
| **Make the command discoverable** | If you use an application factory, add the registration in the factory or in an `init_app` function (as shown in the tutorial). | This ensures the command is attached when the app is created. |

**Bottom line:**  
You only need to modify **your own application files** (e.g., `myapp/__init__.py`, `myapp/cli.py`, or any module that runs `app.cli.add_command`). The core Flask files (`flask/cli.py`, `flask/app.py`) provide the infrastructure, but they are not edited for a custom command – you just use the `app.cli` group that already exists there.

If you ever need to add a **new default command to the Flask CLI itself**, you would have to edit `flask/cli.py` (the `FlaskGroup` definition) or `flask/app.py` (where `self.cli` is instantiated). For most use‑cases, though, the registration pattern above (illustrated by the tutorial’s `db.py` example) is all that’s required.

## Question 7

**Question:** What could be affected if I change the Flask class __init__ method? Ground the answer in the repository and cite sources using numbered citations like [1] and [2].

### Answer

Changing the **Flask.__init__** method will ripple through almost every core capability of a Flask application because that method initializes the attributes that the rest of the framework depends on. Below are the main areas that could be impacted, based on what the repository documents about the Flask and App classes and the session interface.

---

### 1. Application Identity and Resource Loading
- **`import_name`** – used to locate package resources and influences debugging and extension behavior (see **[2]**, **[3]**).  
- **`root_path`** – defines the root of the application files; altering it would change where `open_resource` finds templates, static files, and config files.

> *Impact*: If you modify how these values are set, extensions that rely on the import name or on the root path may load the wrong modules or resources, breaking debugging information or feature detection.

---

### 2. Static File Serving
- **`static_folder`** and **`static_url_path`** – determine where static assets live and how they are accessed (see **[2]**, **[3]**).  
- **`static_host`** and **`host_matching`** – affect the URL that static files are served from.

> *Impact*: Changing the initialization logic could cause static routes to point to the wrong directories or generate incorrect URLs, resulting in 404 errors for CSS, JavaScript, images, etc.

---

### 3. Template Handling
- **`template_folder`** – sets the folder that `render_template` searches (see **[2]**, **[3]**).

> *Impact*: A different template folder would change which templates are rendered, potentially causing view functions to display unintended content or fail to find templates.

---

### 4. Configuration and Instance Path
- **`instance_path`** and **`instance_relative_config`** – control where the *instance* folder resides and whether config files are resolved relative to that folder (see **[2]**, **[3]**).

> *Impact*: Modifying these parameters can break loading of per‑deployment configuration files (e.g., `config.py`), affecting security settings, database URIs, feature flags, etc.

---

### 5. Routing and Host/Subdomain Matching
- **`host_matching`** and **`subdomain_matching`** – enable or disable more sophisticated URL matching based on host or subdomain (see **[2]**, **[3]**).

> *Impact*: Adjusting the initialization could unintentionally disable host‑aware routing or subdomain handling, causing routes to match incorrectly or not at all.

---

### 6. Session Management
- The **`session_interface`** attribute (documented in the session interface description **[1]**) is normally set after the app is created, but the base **Flask** object still creates a default session interface during initialization. Changing `__init__` could alter that default or affect how `session` works across requests.

> *Impact*: A different default could break session persistence, security (e.g., cookie‑based sessions), or cause concurrency issues if the new interface isn’t thread‑safe.

---

### 7. Extension Initialization
Many Flask extensions (e.g., Flask‑SQLAlchemy, Flask‑Login) hook into the application during its creation, often reading the same attributes listed above. Because extensions typically receive a reference to the app at import time or first use, any change to the initialization parameters will be reflected directly to those extensions.

> *Impact*: Extensions may load the wrong configuration, point to the wrong database, or misinterpret the request context, leading to silent misbehavior or runtime errors.

---

### Summary of Affected Areas
| Area                | Relevant Parameters / Attributes | Potential Consequence                               |
|---------------------|----------------------------------|-----------------------------------------------------|
| Resource & Debug    | `import_name`, `root_path`        | Wrong module discovery, broken debug info           |
| Static Assets       | `static_folder`, `static_url_path`, `static_host` | Incorrect static URLs, 404s                     |
| Templates           | `template_folder`                | Views render wrong or missing templates             |
| Configuration       | `instance_path`, `instance_relative_config` | Config files not loaded, security issues         |
| Routing             | `host_matching`, `subdomain_matching` | Routes mis‑match, host/subdomain handling broken |
| Sessions            | `session_interface` (default)    | Session storage broken, cookie‑security issues      |
| Extensions          | All of the above (passed to extensions) | Extensions mis‑configured, runtime errors       |

---

### What to Watch For
1. **Backwards Compatibility** – The documented defaults are part of the public API. Changing them without providing clear fall‑backs can break existing user code.
2. **Thread‑Safety** – The session interface note **[1]** warns that multiple requests may read/write sessions concurrently. A new initialization that does not preserve safe defaults could introduce race conditions.
3. **Testing Impact** – Because `__init__` touches so many subsystems, unit and integration tests that rely on the default app behavior are likely to fail unless they are updated.

---

**In short**, because `Flask.__init__` sets the foundation attributes used for resource resolution, static and template handling, configuration loading, routing behavior, session handling, and extension configuration, any modification to it can affect virtually every other part of a Flask application. Careful review of the changes and thorough testing are essential to ensure that the application continues to work as expected.

### Answer

**How Flask’s request‑ and application‑wide globals are wired together**

In Flask the “global” objects that a view function can refer to (`request`, `session`, `g`, `current_app`) are not stored in ordinary module‑level variables.  
Instead they are **proxy objects** that retrieve their value from the *current* **`AppContext`**. The `AppContext` (see excerpt [4]) holds:

* the **application** (`app`) – used by `current_app`  
* the **request data** (`request`, `session`) – present only when the context has a request (`ctx.has_request` is `True`)  
* the **“g” namespace** (`g`)

All code that wants to read or write these globals does so by asking the current `AppContext` for its attributes. The actual proxy definitions live in `flask/globals.py` (a file that is part of the repository). Each proxy calls a tiny getter, for example:

```python
# flask/globals.py  (conceptual – not in the excerpts)
request = LocalProxy(lambda: _cv_app.get(None).request)
current_app = LocalProxy(lambda: _cv_app.get(None).app)
g = LocalProxy(lambda: _cv_app.get(None).g)
```

The **context variable** that holds the active `AppContext` is `_cv_app`. It is used throughout the `ctx` module:

* `has_request_context()` checks `(_cv_app.get(None) is not None and ctx.has_request)` [2]  
* `has_app_context()` checks `(_cv_app.get(None) is not None)` [3]  
* `copy_current_request_context()` raises a `RuntimeError` when `_cv_app.get(None)` is `None` because no request context exists [1]

When a request arrives, `Flask.wsgi_app` creates a request‑context `AppContext` via `self.request_context(environ)` [5] and pushes it (`ctx.push()`). The pushed context becomes the value of `_cv_app`. While it stays on the stack the proxy getters find a non‑`None` context and return the appropriate attribute (`request`, `session`, `g`, `app`).

**What happens when you access a global outside an active context?**

* **Request globals (`request`, `session`)** – `has_request_context()` returns `False` if `_cv_app` is `None` or the context’s `has_request` flag is `False` [2]. Because the proxy getter calls `_cv_app.get(None)`, it receives `None` and raises a `RuntimeError` (the same error that `copy_current_request_context` emits when no request context exists) [1].

* **Application globals (`current_app`, `g`)** – `has_app_context()` returns `False` when `_cv_app.get(None)` is `None` [3]. The proxy for `current_app` and `g` therefore also raises a `RuntimeError` (typically “Working outside of application context.”) when there is no `AppContext` pushed.

In short:

| Global | Proxy source | Context required | Behaviour outside context |
|--------|--------------|------------------|---------------------------|
| `request` / `session` | `_cv_app.get(None).request` / `...session` | Request‑context (i.e. `ctx.has_request == True`) | Raises `RuntimeError` (“Working outside of request context.”) |
| `current_app` / `g` | `_cv_app.get(None).app` / `...g` | Any `AppContext` | Raises `RuntimeError` (“Working outside of application context.”) |

These behaviours are enforced by the proxy getters and are reflected in the helper functions `has_request_context` and `has_app_context`, which you can use to test before you touch the globals.

**Key citations**

* `[1]` – `copy_current_request_context` raises `RuntimeError` when `_cv_app.get(None)` is `None`.  
* `[2]` – `has_request_context` returns `False` under the same condition.  
* `[3]` – `has_app_context` returns `False` when `_cv_app.get(None)` is `None`.  
* `[4]` – `AppContext` class holds the request, session, `g`, and `app` objects.  
* `[5]` – `Flask.request_context` creates an `AppContext` with request information.  
* `[6]` – `Flask.app_context` creates an `AppContext` without request information.  

Thus, the repository implements request‑ and application‑wide globals as context‑bound proxies, and accessing them when no matching context is active results in a clear `RuntimeError` that tells you exactly what’s missing.
